エッジ機器による音声倉庫管理：構築・導入・実測結果

利用上の注意

これは作業支援ツールであり、認証済みの在庫記帳システムではありません。REST APIにはオフラインキューがなく、ネットワークやサービスの停止中に送ったリクエストは失敗し、復旧後に再送されません。

このソリューションでできること​

作業者が入荷口で「リンゴを10箱入庫」と話すと、ラックのSenseCAP Watcherがそれを聞き取り、同じ建物内のreComputerゲートウェイ上の倉庫データベースに入庫記録が書き込まれます。「リンゴの残りは？」と聞けば音声で答えます。入力もメニュー操作も不要で、手は荷物から離れません。

入荷口、ラック通路、フォークリフトの運転席など、取引がキーボードから離れた場所で発生する現場や、教育コストが見合わずWMSを導入してこなかった小規模倉庫向けです。

  • オープンソース実装： github.com/suharvest/warehouse_system
  • 構成の選択と導入： 参考設計ページ

音声とデータベースは**MCP（Model Context Protocol）**でつながります。倉庫システムは在庫操作をそれぞれMCPツールとして公開し、Watcher上の音声エージェントがMCPクライアントとしてこのエンドポイントに接続します。音声で扱う操作を増やすときはツールを1つ追加するだけで、音声モデルの再学習は不要です。既存のERP/WMSと連携する場合は、相手側のデータインターフェースを同じツール群に対応付けます。

  • Watcherは設置すればすぐ使える

    SenseCAP Watcherは音声エージェントと顔認証のファームウェアを搭載しています。書き込んでステーションに設置すれば、作業者の本人確認をしながら音声で入出庫を登録できます。

  • データは現場に残る

    倉庫データベースは現場のreComputerゲートウェイで動作します。Tier 3では認識、LLM、音声合成も構内に置き、導入後は外部サービスを呼び出しません。

  • オープンソース、既存ERP/WMSと接続可能

    倉庫システムのコードは公開されています。既存システムとの接続は、相手側のデータインターフェースを同じMCPツールに対応付けるだけで、対応付けのコードは数十行程度です。

  • 再学習なしでコマンドを追加

    音声操作を1つ追加するには、MCPツールを1つ登録します。Watcherのファームウェアは変更不要です。

ダッシュボードに表示される内容​

発話が終わると、結果がゲートウェイのダッシュボードに表示されます。在庫ページには品目ごとの現在数量と直近の変動が表示されます。

取引ページには入出庫の記録が1件ずつ、バッチ番号、作業者、入力元（音声またはREST）とともに表示されます。

作業者の名簿はユーザーページで管理し、顔認証はこの名簿と照合します。

必要な機器​

機器の役割は3つです。どれを購入するかは、データと音声AIをどこで動かせるかで決まります。

① 音声端末：SenseCAP Watcher。 すべてのTierで必須で、作業ステーションごとに1台です。プロセッサを2つ搭載し、ESP32がXiaozhi音声エージェント（ウェイクワード、録音、ストリーミング、MCPクライアント）を、Himax WE2が作業者確認用の顔認証ファームウェアを実行します。

② エッジゲートウェイ。 倉庫システムを実行し、セルフホストのTierではMCPエンドポイントも実行します。顔認証をゲートウェイ側に移せるか、1台で何ステーションを扱えるかはこれで決まります。

③ オンプレミスAIホスト。 認識、LLM、音声合成をすべて構内に置く必要がある場合にだけ必要です。

型番この設計での役割選ぶ条件
SenseCAP Watcher音声端末、MCPクライアント、オンデバイス顔認証必須。ステーションごとに1台
reComputer R1125-10倉庫システムを実行するエッジゲートウェイ在庫データを現場に置く、作業者20人以下、顔認証はWatcherで実行
reComputer Industrial R2135-12Hailo-8アクセラレータ搭載エッジゲートウェイ作業者が20人を超える場合、またはライブネス検知が必要な場合
reComputer Super J4012倉庫システム、顔認証、セルフホスト音声サービスを1台で実行2〜3ステーションで1台を共有する場合
reComputer Robotics J5011オンプレミスLLMと音声処理、外部サービス呼び出しなし施設をオフラインで運用する必要がある場合

Watcherが端末内に保存できる顔テンプレートは最大20件です。作業者が20人を超える場合は認識をゲートウェイ側に移す必要があるため、20人以下ならR1125、20人を超えるならHailo-8搭載のR2135を選びます。

その他の前提：Watcherは2.4 GHz Wi-Fiにのみ接続します（5 GHzのみのSSIDはプロビジョニングのスキャンに表示されません）。ゲートウェイは同じLAN内に置きます。Tier 3の導入手順では、NVIDIA container runtimeと約10 GBの空きディスク（音声モデルとLLMエンジンのファイル）を事前チェックします。

選定における制約・非推奨条件​

  • 完全オフライン LLM 要件：機密性の高い現場やインターネット環境がない倉庫で音声 LLM を使う場合は、クラウド依存パッケージを避け、reComputer J4012 搭載の Tier 3 を選定してください。
  • オフラインキューの制約：倉庫管理 API にはサーバー側オフラインキューがありません。不安定な無線下ではクライアント側でリトライバッファを実装してください。

現場での構築手順​

手順は3つです。Watcherを設置してファームウェアを書き込み、ゲートウェイでコンテナを起動し、音声経路を接続します。

ステップ1：Watcherを設置する​

作業ステーションに設置する

Watcherは入荷口、ラック通路、フォークリフトの運転席など、作業者が実際に入出庫を登録する場所に設置します。事務所に設置すると、作業者は数量を覚えて歩いて入力しに行くことになります。

書き込みはUSB-C経由で、デバイスはWCH USB-UARTブリッジ（0x1a86:0x55d2）として認識されます。ファームウェアはプロセッサごとに1つで、Xiaozhi音声エージェントをESP32に、顔認証ファームウェアをHimax WE2に書き込みます。

ステップ2：ゲートウェイを起動する​

倉庫システムは1つのDockerサービスです。導入手順はTierごとに異なります。参考設計ページで構成を選ぶと、対応するアプリケーションパッケージをダウンロードできます。

構成を選んでダウンロード 🖱️

導入はSSHでゲートウェイに接続して実行することも、ゲートウェイ上で直接実行することもできます。既存の在庫は、初回起動時に付属のExcelテンプレートで取り込めます。

導入後、ダッシュボードはhttp://GATEWAY_IP:2125にあり、コンテナのヘルスチェックは同じポートのGET /healthです。

ステップ3：音声経路を接続する​

Trial、Tier 1、Tier 2AではSenseCraftが発行したMCPエンドポイントURLを使います。Tier 2BとTier 3ではMCPエンドポイントをポート18004、音声サーバーを18000（管理コンソールは18003）でセルフホストします。Tier 3ではさらに8000でEdgeLLM、8621でOpenVoiceStreamを動かし、導入後は外部サービスを呼び出しません。

利用できるインターフェース​

連携面は2つです。

MCPエンドポイント（ポート18004）：音声側で使用。 エージェントが行える操作はすべてこのエンドポイント上のツールです。コマンドを増やすにはツールを追加登録するだけで、Watcherのファームウェアは変更しません。既存のERP/WMSとの連携は、同じツールに合わせて自社システムのデータインターフェースを実装することで、対応付けのコードは数十行程度です。言い回しの違いはファジーマッチングで最も近い登録済みコマンドに対応付け、そのまま拒否はしません。

REST API（ポート2125）：その他のシステムで使用。 在庫一覧、取引履歴、エージェントの状態をHTTPで取得できます。

インターフェースエンドポイント / ポートペイロード
ダッシュボード + REST APIhttp://GATEWAY_IP:2125在庫一覧、取引履歴、エージェント接続状態
ヘルスチェックhttp://GATEWAY_IP:2125/health倉庫サービス準備完了後に200
MCPエンドポイント18004MCPツールとして公開される在庫操作
在庫データベースwarehouse_dataボリューム内の/data/warehouse.dbにあるSQLite外部BI/ERPジョブからマウントまたはダンプ
音声サーバーWebSocket 18000、管理コンソール 18003Watcher音声ストリーム（Tier 2B、3）
オンプレミスAI8000 EdgeLLM（OpenAI互換）、8621 OpenVoiceStreamチャット補完、認識、音声合成、声紋（Tier 3）

アクセスはAPIキーのロールとテナントで制限されます。書き込みエンドポイントにVIEWキーを使うと403、テナントをまたぐ読み書きも403になります。どちらも実測済みで、「性能と実測データ」に記載しています。

ローカルLLMのスループット​

デバイスモデルスループット条件
reComputer Robotics J5011EdgeLLM Qwen3.5-4B約16 tokens/s上流の数値。実行ログは添付されていません

既知の性能低下​

  • 在庫照会の遅延は同時実行20から悪化します。 p95は同時実行10の404 msから20で824 ms、50で5.5 sになり、対話的な利用には遅すぎます。
  • REST APIにはオフラインキューがありません。 ネットワークやサービスの停止中に送ったリクエストは失敗し、再送されません。再接続とバックオフはMCP音声WebSocketチャネルだけが対象です。対策：ゲートウェイ側でネットワークの可用性を確保し（有線を優先、UPS給電、サービスとクライアントを同じLANに置く）、利用できない時間をデバイスの再起動時間まで縮めるか、クライアント側に書き込みキューを設け、再接続後に順番に再送してバッチ番号で重複を除きます（クライアント側のキューは未実装です）。
