Jetson Orin 上で意思決定モデルを使ってローカルブラウザーエージェントを構築する

今すぐ入手 🖱️

はじめに​

この wiki では、NVIDIA Jetson Orin 上にローカルブラウザーエージェントを構築します。Laya ローカル意思決定モデル（System One モデル）が次のアクションを選択し、Qwen3.5-4B がリクエストの解析とテキスト生成を担当します。 測定は Jetson Orin NX 16GB を搭載した reComputer Industrial J4012 から取得しています。

意思決定モデルは差し替え可能です。このデモでは Laya を使用していますが、構造化されたアクションを JSON で返せるモデルであれば、どれでも置き換えることができます。

実際のテスト結果を見てみましょう。エージェントには、深センから上海への片道直行便を、最安値順に検索し、条件に合うフライトのチケットオプションを表示するよう指示しています。全体の実行プロセスはわずか 32.8 秒しかかかりませんでした。さまざまなブラウザー自動化操作をエージェントに任せたことがある人なら、この時間がかなり有利であることがわかるはずです。

フライトデモ。英語での 1 回のリクエスト、ライブの Trip.com ページ、そしてアシスタントが自動で開く運賃レイヤー。

次に、ホワイトボードを操作して図を描く別のデモを見てみましょう。自然言語でエージェントに描画を指示できるだけでなく、いつでも自然言語で内容の修正を依頼することもできます。

ホワイトボードデモ。描画、再配色、拡張：1 枚のキャンバス上で 3 回のリクエスト、描き直しなし。

前提条件​

  • JetPack 6.2 を搭載した reComputer

LLM はどのように Web ページを操作できるのか？​

LLM エージェントにフライト検索を依頼するところを想像してみてください。エージェントはリクエストを読み、ページを開き、次に何をするか決める必要があります。ある時点では、ページには出発地と目的地のフィールド、日付セレクター、そして Search ボタンが表示されているかもしれません。プログラムは、これらのコントロールを利用可能なアクションとして提示できますが、その中からどれかを選ぶ役割がまだ必要です。

従来のテキスト生成 LLM は、タスクとページの説明を読み、アクションを書き出すことでその選択を行えます。たとえば、Search をクリックするよう指示を返すかもしれません。プログラムはその出力を解釈してクリックを実行します。ページが変化した後、アシスタントは再びページを観察し、次のアクションを問い合わせます。

その指示を生成するために、LLM はまずタスクとページ情報を読み込みます。その後、これまでに書いた内容に依存しながら、答えを少しずつ書き進めます。これらのステップは prefill と decode と呼ばれます。ページが変化した後、アシスタントは次のアクションを決めるために、これらを繰り返すことがあります。

LLM は多くの異なる答えを書くことができます。しかし、プログラム側ですでに 都市を入力する、Search をクリックする、待機する といったアクションのリストを持っていたらどうでしょうか。そのリストから 1 つを選ぶようモデルに依頼することもできます。ここで意思決定モデルの出番となります。

意思決定モデルは何が違うのか？​

意思決定モデルは、現在の状態、目標、および利用可能な選択肢の集合を受け取ります。各選択肢にスコアを付け、1 つを選択して返します。フライトの例では、必要な検索条件が満たされていることを確認したうえで、提示されたアクションの中から Search をクリック を選択できます。プログラムはその選択を実際のページ上のコントロールに対応付け、クリックを実行します。

テキスト生成ではアクションを出力テキストとして生成し、Laya は提示された選択肢にスコアを付けます。

どちらのアプローチも入力を処理し、計算資源を必要とします。テキストモデルも短いアクション ID を生成することができます。

このプロジェクトでは両方のモデルを使用します。Qwen はユーザーのリクエストを解釈し、必要に応じてテキストを提供します。Laya は現在の候補から操作とターゲットを繰り返し選択します。プログラムはツールを提供し、選択されたアクションを実行し、その結果を確認します。

Laya はどのように次のアクションを選ぶのか？​

1 つの意思決定がどのように行われるかを確認するために、ホワイトボードを使ってみましょう。Camera とラベル付けされた緑色のボックスがあり、それを移動したりラベルを変えたりせずに青色にしたいとします。

Make the Camera rectangle background blue. Keep its text and position.

Laya に選択を依頼する前に、プログラムは状況をテキストで記述します。

入力Camera の例
状態Camera は緑色で、そのラベルと位置は既知
目標Camera を青色にし、ラベルと位置を維持する
候補利用可能な赤、緑、青、黄のボタン

これを多肢選択式の質問だと考えてください。プログラムは、キャンバス上に何があり、何を変える必要があり、どのボタンが利用可能かを Laya に伝えます。そのうえで Laya はそれらのボタンから選択します。この記録された例では、目標は直接 Laya に与えられました。

Laya の内部では、エンコーダー がテキストを読み、状況の理解を構築します。すなわち、現在の色は緑で、望ましい色は青であり、ラベルと位置はそのままにすべきだということです。次に 意思決定ヘッド が利用可能な答えにスコアを付けます。このプロジェクトでは、エンコーダーとして mmBERT-base を使用しています。詳細は 固定されたモデル設定 と アーキテクチャのドキュメント を参照してください。

Laya は状態、目標、候補に関するテキストを読み取ります。この実装ではスクリーンショットのピクセルはモデルに送信しません。

この意思決定では、オプション 3 が青いボタンです。Laya がそれを選択すると、プログラムはそのアクション ID color_blue を使って対応するボタンを見つけます。ページやキャンバスが変化すると選択肢も変わるため、プログラムは次の状態を観察するたびに新しいリストを作成します。

結果は 2 つの質問に答えます。何をすべきか？ そして どこでそれを行うべきか？ この例では、Laya は CLICK と青いボタンを選択しました。両方の答えは同じバッチで計算できます。

記録された Camera の意思決定の 1 例。色付きボックスは保存されたシーン値から再構成されています。

記録された結果では、CLICK は 0.9785 のスコアを受け取り、青いボタンは自分の選択肢集合の中で 0.9721 を受け取りました。プログラムはボタンをクリックし、その後キャンバスを再度読み取りました。Camera は青色になり、ラベルと位置は変わっていませんでした。

これらのスコアは、モデルがどの選択肢を好んだかを示します。ターゲットの confidence 値 0.8859 は別のフィールドです。高いスコアだけでは、クリックが成功したか、タスク全体が完了したかを保証できません。

プログラムは適切な選択肢も提示しなければなりません。Laya はリストに存在しないボタンを選ぶことはできません。選択肢が多い場合、ラッパーはそれらをグループに分けて比較することがあります。つまり、1 回のリクエストに複数回のモデル評価が含まれる可能性があります。

モデルの選択から検証済み結果まで​

Laya は青いボタンを選びました。これでタスクは完了したと言えるでしょうか？まだです。ボタンが移動しているかもしれませんし、クリックしてもボックスが変化しないかもしれません。プログラムはアクションを実行し、実際に何が起きたかを確認する必要があります。

Qwen がリクエストを解釈し、Laya が利用可能なアクションの中から選択し、プログラムがそれらを実行して検証します。

Camera の例では、プログラムは次の手順に従います。

  1. 観察: キャンバスを読み取り、利用可能な色ボタンを見つける。
  2. 選択: どのアクションとターゲットを使うかを Laya に問い合わせる。
  3. 確認: 選択されたボタンがまだ利用可能かを確認する。キャンバスが変化している場合は、再度観察する。
  4. 実行: Playwright を使って青いボタンをクリックする。
  5. 検証: 再度キャンバスを読み取る。Camera は青色か？ラベルと位置は変わっていないか？

結果にまだ改善の余地がある場合、プログラムは更新されたキャンバスを使って、リトライ上限の範囲内でループを繰り返します。チェックに合格したら、そのタスクを完了として報告します。モデルが DONE を返した場合でも、プログラムは実際の結果を必ず確認します。

同じ考え方はフライトにも当てはまります。プログラムは日付の選択などのアクションを提供し、その後でルート、日付、その他の要件を確認します。これらのアクションはアプリケーション側で実装されています。Laya はその中から選択するだけであり、自分で新しいツールを作成することはありません。

Jetson Orin ですぐに実行する​

Jetson のデスクトップで、通常のユーザーとしてターミナルを開き、次を実行します：

git clone https://github.com/zibochen6/jetson-browser-assistant.git
cd jetson-browser-assistant
./setup.sh

インストーラーはデバイスをチェックし、分離された uv 環境と対応する CUDA PyTorch を準備し、Chromium をインストールし、固定バージョンのモデルをダウンロードし、llama.cpp をビルドしてサービスを事前読み込みします。sudo なしで実行してください。システムライブラリが必要なときに昇格したアクセス権を要求します。互換性、ダウンロード、トラブルシューティングについては、README とインストールガイドを参照してください。

意思決定モデルが有用になるのはいつか？​

ユーザーの目標や現在の状態が変化し得る一方で、利用可能なツールが限定されている場合、意思決定モデルを評価する価値があります。フライトのフィルターや、既存のホワイトボードオブジェクトの編集はその 2 つの例です。アプリケーション側は依然として現在の状態を観測し、有意義な選択肢を提供し、何が起きたかを検証する必要があります。

常に同じ手順に従う安定したタスクには、決定論的なスクリプトの方が簡単な場合があります。オープンエンドな回答や新しいテキストには、テキスト生成モデルが引き続き有用です。このプロジェクトには同等のスクリプトのベースラインがないため、デモはスクリプトに対する速度や保守性の優位性を示すものではありません。

現在のリリースがカバーしているのは、限定された Trip.com のワークフローと小さなホワイトボードだけです。他の Web サイト、任意の描画、音声、産業用制御には、個別の開発と検証が必要です。Jetson の 16GB は CPU/GPU 共有メモリであり、他のアプリケーションやスワップが利用可能な容量に影響します。

ブラウザとホワイトボードのデモを試す​

デモを実行する前に、時間がどこに費やされているかを見てみましょう。記録されたフライトタスクは合計で 32.8 秒 かかりました。Laya の意思決定はタスク全体で合計約 0.5 秒、Qwen のパースは約 3.5 秒 でした。ブラウザのアクション、ページ待機、チェック、保存も合計時間に寄与します。

記録されたフライトタスクのタイミング。棒グラフは別々のカウンターであり、完全な加算内訳ではありません。このタスクは既存の検索条件を再利用しました。

フライトを検索する​

アシスタントを起動し、Models ready と Task> が表示されるまで待ちます：

./launch.sh

次のタスクを入力し、日付を有効な将来の日付に置き換えてください：

Find one-way flights from Shenzhen to Shanghai on 2026-11-13 for 1 adult in economy. Nonstop only, lowest price first. Show up to 3 options and open the fare options for one matching flight.

ランチャーは Web サイトと、読み取り専用の Live Flow ウィンドウを表示します。Web サイトのみを表示するには ./launch.sh --no-visualize を使用します。候補、Query verified、Fare options opened を確認してください。アシスタントは注文や支払いを送信することなく、運賃オプションのレイヤーを開きます。

同じホワイトボードを編集する​

アクティブなタスクを完了またはキャンセルし、空白のキャンバスを開きます：

./launch-whiteboard.sh --open examples/whiteboard/blank.excalidraw

--open は現在のキャンバスを置き換えます。既存のエクスポートは残ります。Task> で次を入力します：

Draw three labeled boxes: Camera on the left, Jetson in the center, and Display on the right. Connect Camera to Jetson and Jetson to Display with arrows.

完了したら、空白ファイルを再度開かずに 2 つ目のタスクを送信します：

Make Jetson green. Add a box labeled Robot Arm below Jetson and connect Jetson to Robot Arm. Keep everything else.

完了した各ホワイトボードタスクは、編集可能な scene.excalidraw、PNG、スクリーンショット、検証レポートを保存します。ホワイトボードガイドでは、追加の編集や保存したシーンの再オープンについて説明しています。

タイミングは Enter キーを押した時点から開始され、パース、必要なブラウザの起動、推論、UI アクション、待機、検証、保存を含みます。モデルの読み込み、ウォームアップ、入力待ち時間は除外されます。人間の待ち時間は含まれ、別途報告されます。

タスクの実行中に Ctrl+C を押すとキャンセルできます。待機プロンプトで exit または quit を入力すると、モデルとブラウザを起動したまま終了します。./status.sh でサービスを確認し、./stop.sh でプロジェクトのサービスとモデルを停止します。フライトの記録は runs/ に、ホワイトボードの記録は whiteboard-runs/ に保存されます。その他の操作や復旧については、使用ガイドを参照してください。
