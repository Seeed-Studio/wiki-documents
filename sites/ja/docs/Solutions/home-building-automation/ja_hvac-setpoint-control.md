## このソリューションでできること

オフィス、モール、工場の中央 HVAC プラントは通常、フロアが満員でも空いていても同じ設定値を使う
固定スケジュールで動作します。このソリューションはプラントのそばにゲートウェイを置き、HVAC
コントローラーと電力量計を**単一のポイントモデル**に取り込み、建物自身の過去データから設定値を推奨し、
コントローラーへ書き戻します。ただし、現場から値を読み返して送信値と比較した後にだけ、書き込みを適用済みと数えます。

中央プラントのチラー、エアハンドラー、およびそれらの前段にあるコントローラーを対象にします。分離型
エアコン向けではなく、安全ループにも接続しません。

## 必要な機器

必要なのは、既存のコントローラー、電力量計、Dockerホストの3つです。

**① HVACコントローラー** — プラントの前段にある既存機器で、OPC UA、Modbus TCP/RTU、BACnet/IP のいずれかに対応していれば使用できます。プラントを接続しない試験用に、パッケージにはポート4841のOPC UAシミュレーターが含まれます。

**② 電力量計** — Modbus V2レジスターマップの Eastron SDM630 を、Modbus TCP、Modbus TCPゲートウェイ、またはRS-485経由で接続します。読み取り専用ポイントは10個で、三相電圧・電流、総有効電力 (kW)、総力率、周波数、受電有効電力量 (kWh) を含みます。

**③ ゲートウェイホスト** — 購入判断が必要なのはここだけです。サービスは x86-64 または arm64 上のDockerワークロードなので、プラントネットワーク上の既存Linuxマシンを利用できます。

## 現場への導入

3段階で進めます。3番目の段階が、導入を信頼できるものにするかを決めます。

### 1. 配線：成否を決める条件

:::tip[値を信頼する前に電力量計のバイト順とワード順を確認]
組み込みのSDM630テンプレートは、物理メーターで検証済みだからではなく、メーカー公開のデフォルトに合わせて
バイトとワードをビッグエンディアンに設定しています。既知の物理値を持つレジスターを読み、電力量計の表示と比較してください。
もっともらしく見えても誤った電圧・周波数や、逆方向に跳ねる受電電力量は、配線障害ではなくワード順の症状です。
:::

ゲートウェイをコントローラーおよび電力量計（またはModbus TCPゲートウェイ）と同じネットワークに置きます。
Modbus RTUでは、ボーレート、パリティ、unit idを電力量計の設定に合わせてください。不一致はエラーメッセージではなく
タイムアウトとして現れます。**シリアルデバイス用導入プロファイル**を使ってください。標準Dockerプロファイルはホストの
シリアルデバイスを接続しないため、コンテナ内に `/dev/ttyUSB0` は存在しません。

## 自社システムとの接続

導入で公開されるすべての機能は、ゲートウェイホスト上の1つのHTTPポートの背後にあります。北向き公開を有効にしない限り、プラントネットワークの外へデータは出ません。

- **運用者** — `8280` のブラウザーコンソール：ポイントごとの品質を含むポイント表、電力量計登録、予測実行、コマンド受領、アラームバナー。
- **監視** — `GET /system/runtime-metrics`。北向き公開を有効にすると `northbound.spool.queued` と `northbound.spool.dropped` が含まれます。`dropped` を変えずに `queued` が0へ戻ることを試運転で確認します。
- **自社システム** — `8280` の同じコンソールAPIに加え、起動時に導入が待機するヘルスエンドポイント。

### エンドポイント一覧

| ポート / エンドポイント | 提供内容 | インターネット |
|---|---|---|
| `8280` `/` | ブラウザーコンソール | 不要 |
| `8280` `/system/runtime-metrics` | ランタイムカウンター、北向きスプールカウンター | 不要 |
| `8280` `/api/v1/health` | ヘルスチェック。起動時は30秒を許容 | 不要 |
| `4841` | 試験用の組み込みOPC UAシミュレーター | 不要 |

**最も誤読されやすい項目はコマンド受領の読み戻し結果です。** `protocol_acknowledged` はコントローラーがフレームを受理したことを示すだけで、プラントが動いたことは示しません。`matched`、または検出値付きの `mismatched, compensated` と表示される読み戻し列だけが、現場に保持されている値を示します。ロールバックコーディネーターが発行した補正は、取り消した書き込みの直後に独自の受領として現れるため、2つの表を結合せず監査履歴を順に読めます。

コンテナログは10 MBでローテーションし、4世代を保持します（`docker logs missionpack_knn`）。古いログが失われる前に、コマンド監査履歴、ロールバックジャーナル、アラーム履歴をエクスポートしてください。

## エンジニア向け：実装詳細

### ポイントモデル

1つのレジストリに、取得方法にかかわらずすべてのポイントを保持します。上限は**2,000ポイント**で、そのうち**最大50ポイントを書き込み可能**にできます。SDM630の10ポイントは読み取り専用で、50ポイント枠ではなく2,000ポイント枠に算入します。

| トランスポート | この設計での役割 | 制約 |
|---|---|---|
| OPC UA | HVACコントローラーの読み書き | 導入ごとにエンドポイントを設定。組み込みシミュレーターは4841 |
| Modbus TCP | 電力量計とコントローラー | ソースごとにunit idとポート。直接接続またはTCPゲートウェイ経由 |
| Modbus RTU (RS-485) | 電力量計 | シリアルデバイス用導入プロファイルが必要。標準プロファイルはホストのシリアルデバイスを接続しない |
| BACnet/IP | エアハンドラーの読み書き | 書き込みは優先度を使用し、`Null` で解放。**COV購読、BBMD登録、MS-TPは未実装** |

デバイステンプレート（組み込みSDM630テンプレートを含む）は**256行を上限とする厳密なCSV**を生成し、組み込みテンプレートも手書きテンプレートと同じパーサーを通ります。上限を超えるカスタムテンプレートは同じパーサーによって拒否されます。

### 書き込み経路：凍結・書き込み・読み戻し・比較

すべての書き込みは次の順序で実行されます。

1. ポイントの直近正常値、品質、タイムスタンプ、BACnet優先度を固定します。
2. 認可された書き込み経路で書き込みます。書き込み有効フラグと書き込みポリシーの制約を受け、補正も同じ制約を受けます。
3. バッチ完了後に `settle_seconds` 待機します。
4. ポイントを再読し、`readback tolerance` の範囲内で比較します。
5. **品質が `good` でない読み戻しは、どのような値でも検証成功になりません。**

読み戻しと補正はバッチ内ではなく**バッチ後**に実行するため、サイクル遅延には含まれません。次のバッチは前のバッチが終端状態になるまで待機し、ポイントごとに実行中の書き込みを最大1件に保ちます。

**検証対象はModbusポイントだけです。** BACnet出力は、本番サイクルが書き込み優先度を提供せず、補正時にどの優先度を解放すべきか分からないためスキップされます。

### ロールバックとアラーム

ロールバックのトリガーは、読み戻し不一致、ソース停止、予測無効化、オペレーター中断、バッチの部分適用の5つです。BACnetポイントは書き込み時の優先度で `Null` を使って解放し、Modbusポイントは適用順の逆順で復元します。

アラームは5種類で、**イベントではなく原因で識別**します。同じ障害が繰り返されても、2つ目を開かず未解決のアラームを再利用します。

| アラーム | 重大度 | 理由 |
|---|---|---|
| `source-offline` | warning | プラントは直前の設定値を維持 |
| `stale-sample` | warning | 同上 |
| `write-failed` | warning | 同上 |
| `readback-mismatch` | warning | 同上 |
| `compensation-failed` | **critical** | プラントが不明な状態に残される |

アラームの確認操作はオペレーターが認識したことを記録します。**解除できるのは復旧だけ**で、復旧イベントには解除対象アラームのIDが含まれます。同じ障害で毎回新しいアラームが開く場合は、原因フィールドが異なっています。ソースIDとポイントIDを比較してください。

### パラメータと出荷時の値

導入フォーム（`devices/deploy.yaml`）：

| パラメータ | 出荷時のデフォルト | 注記 |
|---|---|---|
| Control Mode | `observe` | オペレーターが変更するまで書き込みなし |
| Minimum / Maximum Setpoint | 18 / 30 °C | **プレースホルダー** |
| Maximum Change / Change Window | 1.0 °C / 300 s | **プレースホルダー** |
| Mode whitelist | off / fan / cool / heat / auto | **プレースホルダー** |
| Safety Baseline Approved By | *(blank)* | 空欄により基準値は未承認として報告される |
| Readback Delay | 10 s | |
| Readback Tolerance | 0.05 | |
| Stale Sample Threshold | 60 s | |
| Meter TCP Port / Unit ID | 502 / 1 | |
| Serial device / baud | `/dev/ttyUSB0` / 9600 | 19200と38400も選択可能 |

導入変数ではなくコンソールで作成する予測実行設定：

```json
{
  "schema_version": "prediction-run.v3",
  "interval_seconds": 60,
  "rollback": { "enabled": true, "settle_seconds": 2.5 }
}
```

**実行設定で指定しない限り書き戻し検証は無効です。** `rollback` セクションのない設定は、新しい書き込み経路を暗黙に追加せず `enabled: false` に移行します。実行開始時にセクションを明示してください。`settle_seconds`（0–30、デフォルト1.0）は**ソースの収集間隔より長くする必要があります**。短いと、読み戻しが書き込み前の値を見て、存在しない不一致を報告します。

予測モデルは、タイムスタンプ、設定値、測定温度、消費電力の列を持つCSVまたはExcelとして取り込んだ、建物自身の過去運転データに対するKNNです。一般的な曲線ではなく対象建物から学習し、コントローラーへの送信を許可する前に予測をコンソールで確認できます。

## 付録：実測データ {#measured-data}

この節は数値を確認したい読者向けです。読み飛ばしても導入には影響しません。ここにある値はすべて、建物ではなく**開発用ハードウェア上のプロトコルシミュレーター**で測定しました。明記しない限り各値は単一サンプルで、独立した再現測定はありません。

### 測定項目

| 項目 | 状態 |
|---|---|
| 2,000ポイントのサンプリングスループット | **測定済み**、180秒を1回実行 |
| 予測サイクル遅延 | **スモーク測定**、n = 4サイクル |
| 制御受付遅延 | **スモーク測定**、n = 2サイクル |
| 24時間連続実行 | **保留中。** 同じホストで2026-09-05から2026-09-06までソークを実行したが判定未完了。7日間・30日間の実行は未開始 |
| ロールバックとアラームのエンドツーエンド | **予測サイクルに組み込み済みだが、プロトコルシミュレーターのみで実行** |

### 容量

| 指標 | 値 | 条件 |
|---|---:|---|
| サンプリングスループット | 349.99 events/s（350.0目標の99.99%） | 2,000ポイント、4プロトコルソース |
| 予測レート | 0.939 cycle/s | 同じ実行 |
| プロセスグループRSSピーク | 217.3 MiB | 同じ実行 |

3行すべての条件：4プロトコルソースにまたがる2,000ポイント、OPC UAとModbusは5秒、BACnetは10秒間隔でサンプリング、ループバックのみ、reComputer R2000シリーズ（arm64）で**180秒**、キャプチャ `capacity-smoke` r14、upstream `b5fe4cc`。この長さの1回実行は容量スモークテストであり、安定性の結果ではありません。

### 遅延

| 指標 | 値 | 条件 |
|---|---:|---|
| 予測サイクル遅延 | 最大46.27 ms | n = 4サイクル |
| 制御受付遅延 | 最大1.41 ms | n = 2サイクル |

どちらも `northbound-smoke` リグのベースラインにおけるランタイム指標で、upstreamは `f831bae` です。**2個と4個のサンプルから負荷下のシステムについては何も分かりません**。コードパスの範囲を示すだけで、導入環境を示すものではありません。

### 既知の未解決不具合

予測ループは各サイクル後に固定間隔でスリープするため、レートは `1/(1.0 + t_cycle)` です。2,000ポイントでは `t_cycle` が約**0.119 s**となり、構造上の上限は**0.894 cycle/s**付近です。これはソークハーネスの0.90ゲートを下回ります。障害を注入しなかった実行を含め、ラウンド3の全実行で再現しました。ループまたはゲートの変更が必要ですが、どちらも未変更です。

### これより悪化する条件

- **シミュレーターではなく実際の現場機器。** 上記の数値はすべて、このリポジトリ独自のプロトコルシミュレーターをループバックで使用したものです。実際のコントローラーではネットワーク遅延、再試行、タイムアウトが加わります。
- **バイト順。** 試運転で電力量計の表示と照合するまで、スケーリングされた電力量計ポイントの信頼性はメーカー公開デフォルトに依存します。
- **自社プラントでのロールバックとアラーム。** どちらも上流の予測サイクルに組み込み済みですが、常に応答するシミュレーターは、応答しないことがあるプラントとは異なります。書き込み有効化前に source-offline、readback-mismatch、stale-sample を意図的に試してください。
- **180秒を超える実行。** 24時間ソークの判定は未完了で、より長い実行は開始されていません。
