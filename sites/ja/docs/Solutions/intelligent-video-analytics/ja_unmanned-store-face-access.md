これは**認証済みのセキュリティ製品でも、人命安全システムでもない**。認識精度とライブネスによるなりすまし拒否率は、

## このソリューションが行うこと

人が常駐しないドアのカメラが顔を認識し、パッシブ・ライブネス検査を通過したことを確認して、現在の顔ライブラリ、
スケジュール、ブロックリストと照合する。すべての条件を満たした場合だけ、独立した 12/24 V 電源で動くロックを切り替える
リレーにパルスを送る。許可・拒否を問わず、すべての判定は MQTT に公開され、コンソールで検証できるハッシュチェーン監査ログに追記される。

無人または少人数運営の店舗の従業員入口・倉庫・裏口、名簿が毎週変わり登録をセルフサービスにしたい共有オフィス、
スループットより通過者の記録が重要な機器室、既設の RTSP カメラを交換したくない現場に適している。

## 必要なハードウェア

3 つのデバイス役割と 1 台のホスト、そして曲げてはならない 1 つのルールがある。

**① ドアのカメラ。** デバイス内蔵センサー（reCamera Pro または標準 reCamera）か、別ホストへ映像を送る既存の RTSP カメラを使う。実際に人が立ち止まる距離で、1 人の顔がフレームの十分な部分を占めるよう、顔の高さ付近に取り付ける。逆光の出入口とガラスの反射が典型的な失敗要因なので、両方を想定して取り付け位置を確認する。

**② 認識と判定を行う装置。**

| 認識ホスト | 認識の実行場所 | 導入形態 | ハードウェア状態 |
|---|---|---|---|
| reCamera Pro (RV1126B) | カメラ上で既存の顔認識アプリと並行して実行 | `/userdata/f1-access` 配下の標準ライブラリだけで構成した Python モジュール群。Buildroot のため Docker、dpkg、systemd はない | ライブラリ経路と合成イベントによる GPIO 読み戻しを実機で確認 |
| 標準 reCamera (SG2002 / CV181x) | カメラ上の 1 つのネイティブプロセスで検出、埋め込み、まばたき融合付き 2 ヘッドのテクスチャ・ライブネス、照合を実行 | 標準ライブラリだけの小さなデーモンを手動コピー。コンテナなし | 2 回のプローブ実行でライブラリ経路を確認 |

**③ リレー。これが曲げてはならないルールである。** ロックは必ずリレーまたは無電圧接点の後段に置き、演算ボードとは分離した専用の 12/24 V 電源で動かす。ロックは 300 mA
〜 1 A を消費するが、GPIO ピンとフォトカプラ絶縁デジタル出力が扱うのは mA 単位である。4 つの設定 —
`active_high`、`pulse_ms`、`relay_contact`、`fail_mode` — は設置ごとに設定し、意図的に既定値を持たせない。フェイルセーフ電磁ロックを常開接点に配線すると恒久的に開いたままになり、誰かが試験するまで正常な設置に見えてしまうためである。

**④ クラウドまたはオンプレミスのホスト。** Docker を備えた amd64 または arm64 の Linux マシンで、GPU は不要。顔ライブラリサービス、管理コンソール、MQTT ブローカーを実行する。すべてのドア側デバイスから到達でき、時計も正しくなければならない。RTC のないデバイスは HTTP の `Date` ヘッダーから時刻補正を得る。2 つのコンテナイメージはまだレジストリにプッシュされておらず、compose ファイルには使用予定のタグとその旨が冒頭に記載されている。

## 現場への導入方法

2 つの部分に分かれ、順序が重要である。

### 1：ドアを配線する — LED、リレー、ロックの順

LED で極性とパルス幅を確認し、リレーで接点が作動する音を確認してからロックを接続する。フェイルセーフ電磁ロックは COM と NC、フェイルセキュアの電気錠は COM と NO に通す。逆にするとドアが恒久的に開いたままになるため、`relay_contact` に既定値はない。

**GPIO ピンが空いていると仮定してはならない。** 調査した reCamera Pro では `gpio131` がすでに export され、別のアプリケーションに駆動されていた。アクチュエータは現在状態が設定したアイドル状態と異なるピンでは起動せず、明示的に指示されない限りピンを奪わない。reCamera 2002 HQ PoE のベースボードの 6 ピンヘッダーには 3 本の IO ライン — D1 = sysfs 490（多重化されていない唯一の線）、CLK = 487、SMD = 488 — があるが、ヘッダーのレベル極性と供給可能な電流はベンダー文書にない。そのため、メーターと LED で確認するまでロックを接続してはならない。J20 では設計仕様上 DO1–DO4 が sysfs 463/464/465/462 だが、対象イメージがそれらを同じ方法または `Jetson.GPIO` 経由で公開するかは、ハードウェアで確認する必要がある。

クラウド側は `assets/cloud/` の compose ファイルにある顔ライブラリサービス、コンソール、ブローカーで構成する。トークンを設定しないとコンソールは起動を拒否し、共有トークンには 3 つの役割がある。viewer は読み取り、operator は `unlock` / `hold_open` / `lock` の発行、admin は登録・削除・ロールバックを行う。**平文 HTTP 上の共有トークンは認証ではない**ため、前段で TLS を終端すること。付属ブローカー設定は匿名の平文で、ベンチ用である。設計では TLS、デバイスごとの ID、トピック ACL を要求しており、付属設定には 3 つとも含まれない。

LAN 上では平文の `http://` ライブラリ URL も許可されるが、マニフェストへの HMAC-SHA256 署名が必須である。キーがなければデバイスは起動を拒否する。この署名は通信中の改ざんを防ぐが、デバイスを開ける人物は防げない。デバイスキーが漏えいすれば、誰でもライブラリを偽造できる。

## 自社システムへの接続

インターフェースは 5 つの MQTT トピックと 2 つの HTTP サーフェスで構成される。

| トピック / エンドポイント | ペイロード | Retained |
|---|---|---|
| `access/v1/events` (MQTT 8883, QoS 1) | 判定ごとに 1 つの JSON — 下記参照 | No |
| `access/v1/status/{device_id}` | 30 秒のハートビート：アクチュエータ状態、ライブラリバージョンとモデルタグ、ライブネスのロード状態 | Last will のみ |
| `access/v1/commands/{door_id}` | `unlock`、`hold_open`、`lock` | **Never** |
| `access/v1/receipts/{command_id}` | 1 つのコマンドの最終状態 | No |
| `access/v1/relay/{relay_id}/set` と `/state` | MQTT リレープリセットのみ。`state` は物理接点を報告し、ドアが開いているかは報告しない | `set` は no、`state` は yes |
| `GET /v1/facedb/current`、`GET /v1/facedb/{version}` (HTTP 8080) | ライブラリ配布の全サーフェス。分割・再開可能なダウンロードには `Range` を使用 | — |
| `/api/events`、`/api/devices`、`/api/persons`、`/api/audit/verify` (HTTP 8088) | 3 役割のトークンゲートの背後にあるコンソール API。匿名読み取りなし | — |

### イベントペイロード

```json
{
  "schema": "access-event/v1",
  "event_id": "6f1a2c3d-4e5f-4a6b-8c7d-9e0f1a2b3c4d",
  "time": "2026-09-06T03:20:11Z",
  "device_id": "door-front-01",
  "person_id": "p_alice",
  "anonymous_id": null,
  "score": 0.7412,
  "threshold": 0.62,
  "liveness": { "passed": true, "score": 0.958 },
  "decision": { "allow": true, "reason": "allowed" },
  "door_action": "pulse",
  "actuator_id": "door-front",
  "facedb_version": 3,
  "model_sha": "3a7f...",
  "clock": { "valid": true, "reason": null, "offset_ms": 12 }
}
```

多くの連携を決めるフィールドは 3 つある。**最初の同期に成功する前の `facedb_version` は `null`** であり、これはバージョン 0 とは異なる「ライブラリがまったくない」状態で、非一致ではなく拒否理由 `no_facedb` として報告される。**`threshold` はその判定で実際に適用された値**なので、しきい値変更は設定ファイルだけでなくイベントストリームにも現れる。**`clock.valid`** は補正後のタイムスタンプを信頼できるかを示す。デバイスはシステム時計を設定せず、オフセットだけを保持する。

### コマンドゲート

コマンドには正確なフィールド一式、UUIDv4 の `command_id`、タイムゾーン付き RFC3339 の `issued_at`、範囲内の TTL が必要で、ID ごとのリプレイテーブルで検査される。再配信されたコマンドは**2 回目にドアを開けない**。元のレシートを再生するため、呼び出し側は照合対象を受け取れる。期限切れは `TTL_EXPIRED` として返り、匿名 ID は拒否される。

`set` トピックとコマンドトピックは決して retained にしない。解錠コマンドを retained にすると、再接続のたびに再生され、停電復旧後にドアが自動で開いてしまう。

## エンジニア向け：実装詳細

### 顔ライブラリ配布：2 つのエンドポイント、プッシュなし

デバイスは `current` をポーリングしてバージョンを比較し、その後にだけファイルを取得する。分割・再開可能なダウンロードには `Range` を使う。そのため有効化遅延はポーリング間隔（既定 30 s）に相当する。HTTP クライアント以外を必要としないデバイス側と、「通知を失ったがライブラリは変更された」状態を作らないことの代償である。

完全な順序は、ポーリング → 比較 → 分割ダウンロード → ファイルごとの SHA-256 → マニフェスト署名 → 新しいマッチャーのロード → **アトミック切り替え** → gallery への書き込み → `op:reload` の ACK である。どの段階で失敗しても旧バージョンを保持する。2 台のハードウェアでは、`gallery.json` を 1 バイト変更したバージョンと、誤ったキーで署名したマニフェストがデバイス上で拒否され、旧バージョンが維持された。中断したダウンロードは再開された。

各バージョンのマニフェストには 5 つのライセンスフィールド — `license_id`、`use_scope`、`redistributable`、`source_revision`、`sha256` — があり、条項が文書だけでなく成果物にも伴う。確認中のライセンスは `license_id: unverified` と `use_scope: internal-only` として記録し、寛容なライセンスとして先に記載して後で訂正することはない。

### 削除バリアと、ロールバックだけでは不十分な理由

人を削除すると、その人を含まない新しいバージョンを発行して削除バリアを書き込む。その人をまだ含むバージョンへのロールバックは、名前を指定して拒否する。バリアがなければ、1 回のロールバックで過去に削除した人が全員ひそかに再登録される。これが、バージョン管理されたライブラリを有用ではなく危険にする失敗モードである。

### ライブネスを密かに無効化できない仕組み

上流の認識サービスはモデルファイルがないと「認識は続け、ライブネスを省略する」状態に劣化する。ドアではこの劣化が開いたドアを意味するため、アダプターは起動時に `/health` を確認し、ライブネスがロード済みと報告しない限り実行を拒否する。`live` が `null` の場合は通過ではなく**失敗**として扱う。検査が実行されなかったことを意味し、独立した理由 `liveness_unknown` として表面化する。

記録しておくべき適用範囲の空白が 1 つある。RKNN バックエンドのライブネスは上流で未実装であるため、RKNN で動くプリセットは「ライブネス強制」を満たせず、その経路でライブネスの境界を埋めてはならない。

### 監査ログ

追記専用の NDJSON で、各レコードが前のレコードのハッシュを持つ。過去の拒否判定を許可に変更するとチェーンが壊れ、`/api/audit/verify` が報告する。ソフトウェアループでは 13 レコードのチェーンが検証に成功し、1 件の拒否を許可に編集すると検証に失敗した。

### 登録と、reCamera Pro におけるモデル空間の隔たり

`face_rec_api` の `buffalo_l` は、ライセンスとは無関係に、Pro にとって運用上適切な埋め込み器ではない。デバイス内蔵の認識器は `rv1126b:scrfd500m+mbf512@fp16` を使い、2 つのモデル空間間のコサイン類似度はおよそゼロである。現在、デバイスのモデル空間のベクトルを生成するクラウド側埋め込み器はないため、**パッケージ化された登録経路は、現時点でこのデバイスの本番利用可能な顔ライブラリを生成できない**。修正には、デバイスのモデル空間と整合するクラウド埋め込み器、またはデバイス補助の登録経路が必要である。上流は後者、つまり画像を送りデバイス上で埋め込みを再計算する形へ移行中だが、パッケージ版はクラウド計算済みのベクトルを配布しており、本ページはその内容を説明する。標準 reCamera の経路には影響しない。デバイス上で埋め込みを行い、このコンソール経由で登録しないためである。

### 測定済みの項目と未測定の項目

上流では 7 つの境界指標を定義している。1 つは測定済みで、6 つはすべての層が空の `status: pending` であり、それぞれ理由を記録している。

| 境界指標 | 状態 | 未完了の理由 |
|---|---|---|
| 顔ライブラリ有効化 | **測定済み** | 標準 reCamera（2 回のプローブ実行）と reCamera Pro（1 回）で実施 |
| 認識 FAR / FRR | pending | ソフトウェアループに実顔モデルがなく、陽性・陰性ペアもなく、どちらのレンズの前にも人がいない |
| ライブネスのなりすまし拒否 / 生体の誤拒否 | pending | 実際のなりすましサンプル（写真、画面、マスク）と Silent-Face の実行が必要 |
| 直接経路の解錠遅延 p95 | pending | カメラからリレーまでの完全なハードウェア経路が必要 |
| MQTT リレー解錠遅延 p95 | pending | ゲートウェイにリレーが配線されていない |
| オフライン耐久性 | pending | 長時間切断したデバイスが必要 |
| 72 時間連続試験：誤解錠 / クラッシュ | pending | ハードウェア上で 72 時間中断なく動かす必要がある |

### 顔ライブラリ有効化遅延

**これは新しいライブラリバージョンを公開してから、デバイスがそのバージョンで動作するまでの時間である。ドアを開ける遅延ではない。** この設計にはドア開放遅延の測定値は存在しない。

| プラットフォーム | 完全な有効化 | 条件 |
|---|---|---|
| 標準 reCamera (SG2002 / CV181x riscv64、ファームウェア 0.2.2) | **p50 491.6 ms、p95 507.8 ms** (n=20) | USB-RNDIS、2 人、16.5 KB ライブラリ。`op:reload` 往復 p50 100.0 ms (n=25) |
| reCamera Pro (RV1126B、Buildroot 2023.02.6) | 62.2 ms (v1)、45.4 ms (v2)。最新状態で変更なしのラウンドは 6.2 ms | Ethernet、1–2 人、20 KB 未満のライブラリ。一貫性ゲート `problems: []` |
| reCamera PoE | — | ハードウェア待ち。デバイス側コードのセルフテストのみ |
| macOS ソフトウェアループ | 3 回中最遅の 11.6 ms (v1/v2/v3: 11.6 / 3.7 / 3.5 ms) | ループバック HTTP、TLS なし、認証なし、損失ゼロ、4 人 × 128 次元の埋め込み 3 個、1 回のみ。**デバイス側の数値ではない** |

**規模による変化。** 標準 reCamera で 2 つの規模を各 1 回実行した。402 人 / 2.86 MB は 9 801.7 ms、1502 人 / 10.66 MB は 22 278.7 ms だった。有効化時間はライブラリサイズに追従するため、大規模ライブラリの初回同期は遅い。491.6 ms がどの規模でも成り立つと仮定せず、初回展開を計画すること。

### 認識イベントから GPIO ピン読み戻しまで（reCamera Pro）

n=22、p50 1.448 ms、p95 2.709 ms。**これは 1 つのリンクの上限であり、ドアの数値ではない。** 入力は人物ではなく合成した認識イベントで、読み戻しは sysfs のため、数値はソフトウェア経路だけの上限であり、外部回路も接続していない。`gpio130` の物理的な身元は device tree の pinctrl 証拠で、拡張ポートの UART4 M0 ピンの 1 つを GPIO に再設定したものと確認されている。これは 3.3 V 系であり、ボード上の 2 つのネイティブ 12–21 V 出力の 1 つではない。レベルと供給可能な駆動電流は自分の個体で測定し、しきい値には `calibration = pending` が付く。

### 解錠時間と拒否（reCamera Pro、再生映像）

**解錠時間** — アプリに最初の再生フレームを渡してから GPIO ピンがアクティブレベルに駆動されるまでの時間で、キャプチャ、検出、ライブネス、照合、ポリシー、ピン書き込みを含み、顔ライブラリの規模ごとに測定した。p50、括弧内は p95、各点 12 回。n=12 のため p95 列は上限として読む。

| カメラ / ホスト | 10 人 | 1 000 人 |
|---|---|---|
| reCamera Pro (RV1126B), f1-access 0.1.1 | **0.62 s** (0.67) | **0.66 s** (0.68) |

ピンは 24 回中 24 回アサートされた。条件：reCamera Pro 上で `f1-access` 0.1.1 アプリ自体を実行、1280x720 フレームを 12.5 fps で再生、ライブネス有効、最小顔サイズ 40 px、照合しきい値 0.40。入力は生身の人物ではなく、市販の動画クリップをデバイス自身のパイプラインで再生したものである。ピン書き込み後の 1 500 ms の接点保持は含めていない。リレーも錠も接続していないため、機械的な応答は数値に含まれない。10 人と 1 000 人のライブラリ間で測定した p50 の差は 37 ms である。

**拒否** — 各行 20 回、同じデバイスとアプリ。40 回は未登録の人物、60 回はレンズの前にかざした画面である。

| 実行 | 顔ライブラリ | ピンのアサート |
|---|---|---|
| 未登録の人物 | 合成 ID 9 件 | 0 / 20 |
| 未登録の人物 | 合成 ID 999 件 | 0 / 20 |
| スマートフォン画面の再生、クリップ A | 10、攻撃クリップから作成したテンプレート | 0 / 20 |
| スマートフォン画面の再生、クリップ B | 10、攻撃クリップから作成したテンプレート | 0 / 20 |
| 画面の静止画像 | 10、攻撃クリップから作成したテンプレート | 0 / 20 |

未登録の人物の 2 行では、ライブラリには合成ベクトルしか入っていないため、クリップ内の人物は登録されていない。画面の 3 行では、テンプレートを攻撃クリップ自体から作成しているため、ライブラリの顔と画面の顔は同一人物である。静止画像の行は表示フレーム 1 枚を静止させたもので、印刷写真は試験していない。

**AI ホストの認識サービス（reComputer J40 シリーズ）。** JetPack 6 の Orin NX 16 GB では、認識サービスは TensorRT エンジンを本体上で 61 s + 62 s + 73 s かけて構築し、起動 214 s 後にヘルスエンドポイントが応答する。1280x720 の RTSP ストリームから取った 1 フレームに対し、顔ボックス、ライブネス判定、512 次元の埋め込みがサーバー時間 24-26 ms で返る（HTTP 経由で p50 30.3 ms、12 リクエスト）。標準 reCamera と AI ホストには解錠時間の数値がない。標準カメラの認識器はフレームを入力する手段のないクローズドなネイティブプロセスであり、AI ホストの試験機にはリレー接点を読み戻すための 2 本目のヘッダーピンがないためである。

### ソフトウェアループで確認できたこと

1 台の macOS 開発機で、偽のアクチュエータ、インメモリブローカー、偽の認識器を使った。3 つのライブラリバージョンを構築・公開・取得し、SHA 検証とアトミック切り替えを行う 52/52 のチェックに合格した。写真（`liveness_failed`）、null のライブネス結果（`liveness_unknown`）、ブロックリストの人、しきい値未満の他人、空フレーム、デバウンス期間内の再出現を拒否するポリシーも確認した。10 フレーム中の解錠パルスは正確に 2 回で、いずれも設定値 1500 ms だった。異なる 2 バージョンへのロールバックは削除バリアにより拒否され、現在のバージョンは変わらなかった。リモート解錠は受理・実行され、期限切れは `TTL_EXPIRED` で拒否され、リプレイは 2 回目のパルスなしに元のレシートを返し、匿名 ID は拒否された。切断後に retained last will が配信され、13 レコードの監査チェーンは検証に成功し、1 件の拒否を許可に編集した後は失敗した。コンソールの 3 つの役割も想定どおり動作した。

これらはいずれも顔認識の性能やなりすまし拒否性能を測定したものではない。プロトコルと状態機械が主張どおり動作するかを測定したものである。

### ライセンス

このパッケージと上流リポジトリのコードは Apache-2.0 である。**モデル重みは異なる。** 顔検出と埋め込みには InsightFace の `buffalo_l` を使う。InsightFace 自身の声明では、コードは商用利用の制限がない MIT だが、トレーニングデータとそのデータで学習したモデルは非商用研究用途に限られる。`buffalo_l` はそのようなモデルであり、`license_id: non-commercial`、`use_scope: non-commercial`、`redistributable: false` である。重みはここには同梱しない。

遅くなってから判明する前に、2 つの帰結を明記する。商用導入では顔バックボーンを商用ライセンスのものに置き換える必要がある。置き換える場合は**すべての顔ライブラリバージョンを再構築する**必要がある。モデル間で埋め込みを比較できず、あるバックボーンで構築したライブラリは別のバックボーンに対して約 0 のスコアになるため、旧バージョンは単に古いのではなく無効になる。マニフェストの `model_tag` ガードが、デバイスによる誤ロードを防ぐ。

パッシブ・ライブネスモデルの MiniVision Silent-Face-Anti-Spoofing は Apache-2.0 で、`use_scope: commercial`、再配布可能、未変更で使用している。

### このページからは分からないこと

- **ドアの前の人を認識できるか。** 同梱のしきい値は出発点にすぎない。設置したカメラで陽性・陰性ペアを走査し、その結果から設定すること。
- **写真を拒否できるか。** 実際のなりすましサンプルに対するライブネス試験はまだ行っていない。
- **ドアが開く速度。** 2 つの解錠遅延境界は未測定で、リレーやロックも配線していない。
- **1 週間連続で動くか。** オフライン耐久性と 72 時間連続試験はいずれも未測定である。
