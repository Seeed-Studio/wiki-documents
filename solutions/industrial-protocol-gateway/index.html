Industrial Multi-Protocol Data Hub: Hardware, Deployment, and Measured Results

Usage notice

This is a protocol integration and data-hub layer, not a certified control or metering system.

What this solution does​

A building, energy or equipment-management integrator arrives on site and finds the data already exists — behind an OPC UA controller, a Modbus meter, a BACnet/IP air handler and an MQTT sensor gateway, four different addressing schemes and four different failure modes. This solution puts all four into one point registry on one edge host, and gives the system above a single MQTT read/write contract. On a new site you connect the controllers and map the points; the protocol layer stays as it is.

Deploy the container, add a source, let discovery propose candidates, confirm the points you want, verify their quality, then publish them — locally on port 1883, northbound to a cloud broker on 8883, or both.

  • Selection and deployment: reference design page

  • Existing devices connect as they are

    Devices that already speak OPC UA, Modbus, BACnet/IP or MQTT are not replaced. They land in one point registry on one edge host, and the layer above gets one MQTT read/write contract.

  • Discover, then confirm

    OPC UA browsing, Modbus unit scanning, BACnet Who-Is and MQTT topic observation propose candidate points; a point becomes managed once you confirm it. Where discovery is incomplete, enter points by hand.

  • 2,000 points at 349.99 events/s

    Four sources of 500 points each at 5/10 s poll intervals, measured in one 180 s loopback run on a reComputer R2000 series.

  • Northbound backfills after an outage

    Events are spooled locally through a 300 s cloud broker outage; on reconnect the backfill is complete (1.000) against a persistent broker and 0.9839 against an in-memory one.

These captures show the console running against simulated and bench controllers. On site, managed points and live telemetry populate directly from the configured controller register maps.

The gateway comes in a rugged industrial DIN-rail enclosure that clips directly onto a standard 35mm rail inside electrical risers or plant cabinets, powered by 24V DC.

What hardware you need​

Two things: the field devices that are already installed, and one host that can reach each of their networks.

① Field devices — whatever already speaks OPC UA, Modbus (TCP or RTU), BACnet/IP or MQTT. Nothing on the plant side is replaced. What you must have per source: the OPC UA endpoint and credentials; the Modbus unit id, register map, byte and word order; a network interface on the BACnet subnet with broadcasts reaching it; and, for MQTT, an explicit topic-to-point mapping. Modbus RTU additionally needs a USB-to-RS-485 adapter unless the host carries RS-485 on board.

② The data-hub host — a plain Docker host, x86-64 or arm64, that decides which field interfaces you get without an adapter and whether anyone can operate the system without a laptop on site:

HostOn-board field I/OWhen to choose it
reComputer R1000 Series
CM4-based IoT gateway		RS-485, RJ45 EthernetEverything is on Ethernet, with at most one RS-485 run
reComputer R1100 Series
CM4-based IoT gateway and controller		RS-485, RS-232, DI/DO, Gigabit Ethernet, CANThe site has RS-232 devices or DI/DO dry contacts as well
reTerminal DM Series
10.1-inch HMI with the same services		RS-485, CAN, Ethernet (CM4104032 variant adds RS-232, DI/DO, terminal block)No permanent computer in the plant room; setup and daily checks happen on the device

The software point ceiling is the same on all three: 2,000 points, 50 of them writable, enforced in code. A 2,000-point workload did not pass the capacity test on the R1000's CM4-class platform (2 GB configuration, tested on a development board), so pick the R1100 or reTerminal DM at that scale; for smaller R1000 deployments there is no measured point count yet. eMMC size decides how much northbound outage spool and command-receipt history stays on the box; the service itself needs about 4 GB free.

Other prerequisites: Docker Engine 20.10 or newer, ports 8280 and 1883 free (or pick unused ones before deploying), and network reachability from the host to every protocol network.

Negative Selection Boundaries​

  • Interfaces and Point Count: If the site requires RS-232, DI/DO signals, or exceeds 1,000 points, avoid R1000 (single RS-485); choose R1100 or reTerminal DM.
  • Headless vs On-Device UI: If the plant room lacks a PC and operators need on-site configuration, avoid headless gateways and select the 10.1-inch reTerminal DM.

How to deploy on site​

One: install hardware — cabinet mounting, power, and bus wiring​

  1. DIN-Rail Mounting and Power Supply:

    • Secure the gateway onto a standard 35mm DIN rail inside the control cabinet or riser box using its built-in mounting bracket.
    • Power supply: industrial regulated DC 12V/24V (wide input range DC 9–36V supported).
    • Surge Grounding: Connect the protective earth (PE) terminal of the gateway chassis to the cabinet equipotential ground bus using a grounding wire (≥2.5mm²) to suppress electromagnetic noise from motors and VFDs.

  2. Network and BACnet/IP Subnet:

    The host needs an interface on the BACnet subnet

    BACnet/IP discovery is broadcast-based. The host needs an interface on the BACnet subnet, and the broadcasts must not be filtered by network switches. Remote Linux deployments should use host networking (network_mode: host). Docker Desktop bridged setups may drop UDP broadcasts; in that case, specify target device IPs manually.

  3. Modbus RTU / RS-485 Wiring and Serial Port Passthrough:

    • Bus Wiring: Use shielded twisted pair (STP) cables. Connect A+ and B- to the corresponding controller terminals. Ground the shielding foil on the gateway side only. Maintain a daisy-chain topology without star branches; terminate both bus ends with 120Ω resistors.
    • Docker Serial Passthrough: The default Docker configuration does not mount host serial devices. When using a USB-to-RS-485 adapter or on-board serial port, explicitly map the device node in docker-compose.yml: 
      services:
        gateway:
          devices:
            - "/dev/ttyUSB0:/dev/ttyUSB0"  # Or /dev/ttyAMA0 for on-board port
          group_add:
            - "20"  # dialout GID to allow non-root container serial access

    Before enabling production writes, verify readback with actual slave IDs and register addresses on the local console.

Two: install the software and bring the first source in​

The per-device steps and application packages are on the reference design page; pick a configuration for your site and download.

Pick a configuration and download 🖱️

  1. Deploy — the local target installs onto the machine running SenseCraft Solution; the remote target installs over SSH onto a reComputer R2000 series or reTerminal DM on the controller network.
  2. Create the first administrator — no registration token is required on first run.
  3. Add a source — OPC UA, Modbus, BACnet/IP or MQTT, then run discovery where it is available: OPC UA browsing, Modbus TCP unit scanning, BACnet Who-Is, MQTT topic observation. Each produces candidates. The wizard asks for address and poll interval per protocol:
  1. Confirm points — only confirmed candidates become managed points. Where discovery is incomplete or unavailable, enter points by hand.
  2. Verify quality before granting write access — check live values and per-point quality on the Points page first.
  3. Configure the data service — the embedded broker, and optionally the northbound publisher.

Difficulty intermediate, about 15 minutes to a running console; bringing in the first controller and checking its data quality takes longer.

Available interfaces​

Data leaves the host through three interfaces:

  • Operators — the browser console on HTTP 8280: source management, the point table, command receipts, plugin management.
  • On-site systems (SCADA, energy platform, your own service) — subscribe to the embedded broker on 1883. Point telemetry arrives under missionpack/v1/{gateway}/points/{point_id}, with presence, command and receipt topics on the same contract.
  • Cloud or central systems — enable northbound publishing to an external broker on 8883. Telemetry is batched at QoS 1, per-source health and last-will status are retained, and a QoS 0 heartbeat runs alongside. The currently published image has no northbound publisher.

{gateway} is the gateway id you set at deploy time, so several hubs can publish to one broker without colliding.

The topic contract​

Topic / portPayloadRetained
HTTP 8280 /Browser console—
missionpack/v1/{gateway}/points/{point_id} (1883)Versioned point telemetry — value, quality, timestamps, revisionsNo
presence / command / receipt topics on the same prefix (1883)Source and gateway presence, commands issued, and the receipt for eachPresence retained
missionpack/v1/{gateway}/telemetry (8883)Northbound batched telemetry envelope, QoS 1No
per-source health and last-will topics (8883)Source health and gateway statusYes

The northbound envelope is missionpack.northbound.v1:

{
  "schema_version": "missionpack.northbound.v1",
  "message_id": "0f3a...",
  "gateway_id": "gw-01",
  "created_at": "2026-09-05T05:01:19.045514Z",
  "samples": [
    {
      "source_id": "ahu-bacnet",
      "point_id": "analog-value:12",
      "ts": "2026-09-05T05:01:18.900000Z",
      "quality": "good",
      "value": 23.5,
      "source_revision": 4,
      "point_revision": 7
    }
  ]
}

source_revision and point_revision: the revision changes when a point is re-mapped, which tells a configuration change apart from a field value change. A consumer that does not check them joins data from before and after a configuration change into one series.

Two limits of the contract:

  • The protocol is MissionPack v1; this release is not Sparkplug B compatible, so a Sparkplug host application needs a translation step.
  • Plain MQTT is telemetry-only. Enable TLS and an authorised control identity before allowing remote commands.

Performance and measured data​

Load was generated by a four-protocol simulator and measured over loopback on one device per tier; there is no site deployment data.

Refresh cycle at 2,000 points​

Conditions for all three tiers: 2,000 points across 4 sources (500 each), run length as noted, loopback only, on a reComputer R2000 series (arm64).

Runtime and key parameters​

The runtime is distributed as a container image (x86-64 and arm64) from sensecraft-missionpack.seeed.cn; there is no public source repository yet.

  • Point ceiling: 2,000 managed points, 50 of them writable, enforced in code.
  • Sampling interval: decides whether 2,000 points run stably, see the table above: OPC UA/Modbus 5 s with BACnet 10 s passes, while 2 s / 4 s already fails.
  • Northbound spool: the size and age limits (512 MB / 86,400 s in the measured runs) set how long an outage the host can absorb; batch size and the QoS 0 heartbeat are also configurable.

Known degradation​

  • Each tighter sampling step moves the result from pass to degraded to aborted; the failing metrics all come from the prediction plugin (PREDICTION_*).
  • The prediction plugin has a structural rate ceiling (not fixed): the loop sleeps a fixed interval after each cycle, so its rate is 1/(1.0 + t_cycle). At 2,000 points t_cycle is about 0.119 s, putting the ceiling near 0.894 cycle/s, below the 0.90 gate the soak test requires.

Next steps​

  • Read/write with independent readback against real OPC UA, Modbus TCP, Modbus RTU (USB-to-RS-485) and BACnet/IP devices on a reComputer R10 series or reTerminal DM.
  • A 72-hour unattended run on the same target hosts, with network, broker, process and device recovery drills during the run.
